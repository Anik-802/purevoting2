# 데이터 흐름과 구조 설명 (학습·발표 대비용)

> 이 문서는 "표 하나가 어디를 거쳐 어떻게 바뀌고 어디에 저장되는가"를 한 번에 설명하기 위한 정리입니다.
> 기준은 `contracts/`(README, hashing.md, chain-interface.md) → `docs/system-design.md`·`decisions.md`·`threat-model.md`
> 순서이며, 이 문서와 다르면 기준 문서가 맞습니다(D-19).
> **구현 상태 기준일: 2026-11-06** (`docs/schedule.md` 1절). 아직 구현되지 않은 부분은 **(미구현: 담당 예정일)** 로 표시했습니다.
> 발표에서는 표시된 부분을 "설계"로만 말합니다.

## 1. 한 줄 요약

**표는 투표자 브라우저가 선거 공개키로 봉인해서 서버 DB에 두고, 링크·투표권은 해시만 저장하며, 블록체인에는 해시·상태·기관
서명만 남깁니다.** 블록체인은 표를 처리·집계하는 곳이 아니라 **기록을 나중에 몰래 고칠 수 없게 증거를 박아 두고, 승인·확정
조건을 검사하는 곳**입니다. 규칙 엔진은 그 증거와 서버 데이터를 대조해서, 이미 기록된 데이터의 사후 변경을 찾아냅니다.

## 2. 구성 요소가 하는 일

| 구성 요소 | 한 문장 역할 | 갖고 있는 것 | 갖고 있지 않은 것 |
|---|---|---|---|
| 투표자 웹 (브라우저) | 투표권을 만들고 표를 봉인해서 보냄 (현재 mock, 실제 연동은 웹 4단계) | 링크 토큰, 투표권(credential), 내 선택 | 다른 사람의 표 |
| 관리자 웹 | 선거 생성, 명단, 링크 발급, 승인 서명, 개표·확정 (현재 mock) | 기관 서명키 (설계: 승인자 브라우저에만. 시연은 한 PC에 모든 키, D-21) | 표 내용 |
| Core API + DB | 선거 상태 관리, 봉인된 표 보관, 개표 | 명단(평문 개인정보), 봉인된 표, 해시들, 선거 개인키(선관위) | 투표자와 표를 잇는 키 |
| Ledger Gateway | 이벤트를 검사해서 체인에 기록, 조회 API (미구현: Harits 11-09) | 원장 이벤트 본문 (개인정보·표 내용 없음. 가명 키·개수·개표 결과는 있음) | 이름, 봉인된 표 |
| 스마트 계약 (PureChain) | 상태 전이, 승인 정족수, 감사 결과, 확정 조건 검사 (일부 미구현, 아래 4절) | 배치 머클 루트, 선거 상태, 서명된 승인·검토 | 표 내용, 개별 표 |
| 규칙 엔진 (R1–R5) | 서버 데이터와 체인 증거를 대조해 조작 탐지 (R4·R5 일부 구현, 실제 연동 진행 중) | view(개인정보 없는 표), 체인 읽기 | DB 직접 접근 |
| AI 감사 에이전트 | FAIL의 근거를 모아 설명 보고서 작성 (AI 또는 템플릿 보고서, 11-13 결정) | 읽기 전용 도구 | 쓰기·결정 권한 |
| nginx (`web` 서비스) | 바깥에서 들어오는 유일한 입구, 경로 차단·요청 제한 (D-29, 작업 중 11-06) | 화면 파일 | 데이터 |

### 무엇이 어디에 저장되나 (3단계)

| 위치 | 저장되는 것 | 누가 볼 수 있나 |
|---|---|---|
| Core DB | 명단(이름·학번), 토큰 해시, 투표권 해시, 봉인된 표, 영수증 해시, 체크포인트 | 선관위(DB 운영자) |
| Gateway 원장 | 이벤트 본문: 해시, 시간 구간, 개수, 가명 voter_key, 개표 결과 | 참여 기관·감사인 (Gateway 조회 API) |
| 블록체인 | 배치 머클 루트, 선거 상태, 기관 서명(승인·검토), finding 기록 | 노드를 가진 모든 기관 |

## 3. 표 하나의 여정

```
① 링크 받기      관리자 → CSV → 투표자          https://<주소>/vote/<선거ID>#t=<토큰>   (메일 발송은 개발용 MailHog, D-16)
② 투표권 만들기  브라우저: credential = 128bit 난수 (서버는 원문을 모름)
③ 링크 사용      브라우저 → Core: redeem(token, H(credential))
                 Core: 토큰 USED 처리 + 투표권 해시 등록 (한 트랜잭션, 서로 다른 스키마)          ← Core 구현됨
④ 표 봉인·제출   브라우저: sealed = sealed_box({"candidate_id": ...}, 선거 공개키)   (미구현: 웹 4단계)
                 브라우저 → Core: ballot(credential, sealed)
                 Core: H(credential) 등록 확인 → 봉인된 표 저장 → 영수증 발급(RECEIVED)        ← Core 구현됨
⑤ 원장 기록      Core → outbox → Gateway: TOKEN_USED, BALLOT_RECEIVED                        ← Core 쪽 구현됨
                 (시각은 시간 구간 단위, 무작위 ID, 구간마다 순서를 섞어서 전송)
                 Gateway: 60초 또는 50건 단위 배치의 머클 루트를 계약에 기록 → ANCHORED  (미구현: Gateway 11-09)
⑥ 체크포인트     Core: 주기마다 6개 테이블 스냅샷 해시를 원장에 기록(CHECKPOINT_COMMITTED)     ← Core 구현됨
⑦ 감사           규칙 엔진: view(체크포인트 k 기준) + 체인 값으로 R1–R5 판정 → 서명해서 체인에 등록
                 (R4·R5 일부 구현, 체인 등록은 계약 11-10)
⑧ 개표           마감 → Core가 원장에서 수락된 표만 복호화해 집계
                 → 개인키를 규칙 엔진·기관 직원·감사인에게 공개(일반 공개 아님, D-23) → R5가 다시 복호화해 대조
                 ← Core 개표 구현됨(가짜 Gateway로 확인, 2026-11-06). R5 재복호화는 미구현(Anik 11-16)
⑨ 확정           Core가 확정 조건 검사 후 ELECTION_FINALIZED 전송 ← Core 쪽 구현됨
                 계약이 직접 다시 확인  (미구현: 계약 확정 조건 11-16, 검토 정족수 11-25)
```

### 단계별로 무엇이 어떻게 바뀌나

| 데이터 | 만드는 곳 | 변환 | 저장 위치 | 체인에 올라가는 것 |
|---|---|---|---|---|
| 링크 토큰 | Core (발급 때) | `token_hash = H(token)` | DB에는 해시만, 원문은 CSV로만 나감 | 토큰 집합의 루트 (`token_set_root`) |
| 투표권 | 투표자 브라우저 | `nullifier_hash = H(credential)` | DB에는 해시만 | 배치 머클 루트에 포함 |
| 선택 | 투표자 브라우저 | 선거 공개키로 봉인(libsodium sealed box) | DB에 봉인된 바이트 | `ballot_hash = H(봉인 바이트)`가 배치 루트에 포함 |
| 영수증 | Core (설계상 브라우저도 미리 계산 가능, 웹 4단계) | `receipt_hash = H({선거, nullifier_hash, ballot_hash})` | DB | 배치 루트에 포함 → ANCHORED |
| 개표 결과 | Core | `result_hash`, `ballot_set_root` | DB, 득표 상세는 Gateway 원장(`TALLY_PUBLISHED`) | `result_hash`만, 확정 시 계약이 대조 |

`H`는 SHA-256, 객체는 RFC 8785로 정규화한 뒤 해시합니다(`contracts/hashing.md`). 같은 입력이면 누가 계산해도 같은 값이 나와야
대조가 성립하므로, 모든 모듈이 같은 해시 벡터(`tests/vectors/hash-vectors.json`)를 통과해야 합니다. 현재 Core·ledger는
CI에 벡터 검사가 들어 있고, rules는 로컬 테스트(`rules/tests/test_hashing.py`)에만 있습니다(CI 미연결). 브라우저 쪽은
미구현입니다(웹 기반 작업 11-10).

## 4. 왜 "서버 + 블록체인 증거" 구조인가

미팅에서 나온 두 방향을 비교하면 다음과 같습니다. **핵심 이유는 속도가 아니라 익명성과 투표 비밀입니다.** 표마다 체인 기록을
하나씩 남기는 방식은 결정 D-22에서 "익명성 비용" 때문에 기각했습니다.

| 기준 | A. 서버 처리 + 체인에 증거만 (**우리 선택**) | B. 모든 처리를 스마트 계약에서 |
|---|---|---|
| 비밀투표 | 봉인된 표는 DB에만. 체인에는 해시만 | 봉인된 표가 체인에 영구 공개. **우리 암호 방식(sealed box)을 계약에서 개표하려면** 개인키를 체인에 올려야 해 누구나 영구히 읽게 됨. 이를 피하려면 동형암호 집계 같은 다른 방식이 필요하고, 2개월 범위를 넘음(D-01) |
| 투표자-표 연결 | 시간 구간·순서 섞기·스키마 분리로 약하게 만듦 (구간당 예상 투표자가 10명 이상일 때만 효과가 있음. v1.4부터 강제하지 않고 웹은 1분 구간이라 대부분의 선거에서 약함, D-10) | 트랜잭션마다 블록 시각·순서와 (단순 구현 시) 보낸 계정이 공개되어 연결이 쉬워짐 |
| 속도 | 접수 응답(RECEIVED)은 즉시, 체인 증거(ANCHORED)는 구간이 끝난 뒤 배치 + 확정까지 수십 초~수 분(시연 설정 60초 구간 기준, 평가 설정 900초 구간이면 최대 십수 분) | 표마다 블록 포함·확정을 기다림(잠정 (1+D)·P ≤ 15초, D-02·D-27). 체인 증거는 A보다 빠르지만 표마다 트랜잭션 |
| 버그 위험 | 계약도 쓰지만(승인·확정 등) 투표 처리 로직은 서버에 있어 고치기 쉬움 | 모든 로직이 계약에 있어 버그 영향 범위가 더 큼 |
| 서버를 얼마나 믿어야 하나 | **사후 감사로 견제:** 체크포인트에 기록된 데이터가 체인의 해시와 다르면 규칙 엔진이 FAIL을 냄. 단, 선관위의 투표 비밀 접근과 기권자 표 끼워 넣기(위협 모델 E4)는 막거나 탐지하지 못함 | 처리 자체는 계약이 하지만, 링크 발급·키 보관·투표자와 송신 계정의 연결은 여전히 서버나 체인 밖에 남음 |
| 남는 약점 | 선관위(DB 운영자이자 개인키 보유자)에 대한 투표 비밀은 보장 못 함 | 위 방식대로면 키 공개 이후 누구에게도 비밀이 없음 |

**발표용 한 줄 답:** "우리는 블록체인을 **표를 처리하는 곳이 아니라 감사 증거를 남기는 곳**으로 씁니다. 체인을 읽는 사람에게는
표 내용을 숨기고, 대신 모든 기록의 지문과 기관 승인을 체인에 박아서, **이미 체크포인트에 기록된 데이터를 서버가 나중에
바꾸면** 규칙 엔진이 찾아내도록 설계했습니다. 확정·승인 조건은 계약이 직접 검사하도록 설계했고, 계약 쪽은 M3(11-26)까지
구현합니다."

### 스마트 계약이 강제하도록 설계한 것 (체인 기록에서는 서버가 우회할 수 없는 부분)
- 선거 상태 전이 순서(개시, 마감, 개표, 확정) — 일부 구현, 확정은 11-16
- 명단 정정·선거 무효를 **원장에 기록**하려면 요청 기관을 뺀 참여 기관 임계값(시연 2)곳의 서명이 필요(D-11) — 미구현: 11-23.
  서버가 서명 없이 **DB만** 바꾸면 계약이 막는 것이 아니라 R4/R5가 사후에 탐지합니다(시험 T05, M2 시연 E2)
- 규칙 엔진 finding 기록(규칙 엔진 키로 서명된 것만) — 미구현: 11-10. 기관의 서명 검토 — 미구현: 11-25
- 확정 조건: TALLY 체크포인트의 R1–R5가 모두 기록되고, 미해결 FAIL·INCONCLUSIVE와 CONFIRMED_ISSUE가 없고, 확정 결과가
  개표 `result_hash`와 같아야 함(D-24, contracts/README 상태기계) — 미구현: 11-16, 검토 정족수 11-25

### 체인이 아니라 규칙 엔진이 잡도록 설계한 것
- 이미 커밋된 체크포인트의 표를 DB에서 수정·삭제하거나, 원장 기록 없이 표를 추가한 경우: 스냅샷 해시, 행 단위 원장 대조,
  `H(봉인 바이트) = ballot_hash` 검사(R5). **단, Core 내부자가 원장 기록까지 맞춰 기권자 표를 넣는 것은 탐지하지 못합니다(E4).**
- 중복 투표, 기간 밖 투표, 개수 불일치(R1–R3)
- 개표 결과 위조: 감사자에게 공개된 개인키로 다시 복호화해 결과와 `result_hash` 대조(R5)
- 실증은 M2(11-19)의 T05·T08 시연에서 합니다. 그 전에는 "설계"로만 말합니다.

## 5. 하지 않는 주장 (질문이 오면 솔직하게)

- **선관위에 대한 투표 비밀은 보장하지 않습니다.** 선관위가 DB 운영자이고 개인키를 가지고 있기 때문입니다(D-23, 위협 모델 S3).
  임계값 복호화·블라인드 서명은 향후 과제입니다.
- **Core 내부자의 기권자 표 끼워 넣기는 탐지하지 못합니다**(E4).
- **강요·매수 방지(영수증 없는 투표)가 아닙니다.** 봉인이 재무작위화되지 않아서, 변조한 클라이언트나 보관한 봉인 바이트로 키 공개 후
  선택을 증명할 수 있고, 매수자가 준비한 암호문을 제출한 뒤 영수증 조회로 확인시킬 수도 있습니다(S6).
- **종단간 검증(E2E verifiability)을 주장하지 않습니다.**
- **시연은 한 PC에서 모든 기관과 노드를 운영합니다.** 실제로 독립된 기관이 아닙니다(D-21).
- **CSV를 받은 관리자의 대리 투표는 막지 못합니다**(S4).
- 전체 목록은 `docs/threat-model.md`의 "Claims we must NOT make"에 있습니다.

## 6. 예상 질문과 답

| 질문 | 답 |

| 블록체인에 표가 저장되나요? | 아니요. 표의 해시를 60초(또는 50건) 묶음의 머클 루트로만 올립니다. 표 내용은 DB에 봉인된 채로 있습니다 |
| 서버 관리자가 DB를 고치면요? | 이미 체크포인트에 들어간 행을 바꾸면 스냅샷 해시가 체인 값과 달라져 R5가 FAIL을 내도록 설계했고, FAIL이 해결되지 않으면 계약이 확정을 거부합니다(M2에서 T05·T08로 시연, 계약 확정 조건은 11-16 구현). 다만 원장 기록까지 맞춘 내부자의 표 끼워 넣기는 못 잡습니다(E4) |
| 투표하자마자 체인에 들어가나요? | 시스템 이벤트(선거 개시 등)는 묶지 않고 개별로, 투표 이벤트는 시간 구간이 끝날 때 섞어서 묶음으로 들어갑니다. 둘 다 Core가 구간 끝에 내보내므로 원장과 view에는 정확한 투표 시각이 남지 않습니다. 단, 구간당 투표자가 적으면 연결될 수 있습니다(D-10, 위협 모델 S1) |
| 누가 누구를 찍었는지 서버가 알 수 있나요? | 링크 사용 기록과 표는 서로 다른 스키마에 저장되고 잇는 키가 없습니다. 하지만 DB 관리자는 트랜잭션 메타데이터로 연결할 수 있고, 이는 공개된 한계입니다(위협 모델 S2) |
| 왜 퍼블릭 체인이 아닌가요? | 기존 PureVoting 사설 체인(PureChain)을 재사용하고, 참여 기관이 검증 노드를 하나씩 운영하는 구조로 정했습니다(D-02·D-03). 배포 설정상 가스 가격도 0입니다. 다만 시연에서는 한 사람이 노드 3개를 모두 운영하므로 독립 기관이라는 효과는 주장하지 않습니다(D-21) |
| AI가 판정하나요? | 아니요. 규칙 엔진이 판정하고, AI(또는 AI가 아닌 템플릿 보고서)는 근거를 모아 설명하는 보조입니다. 확정은 보고서와 무관합니다(D-15, D-24) |
| 외부에서 어떻게 접속하나요? | 서버는 데모 PC에서 돌고, Tailscale Funnel이 HTTPS 공개 주소를 붙여 줍니다. 바깥에서 닿는 것은 nginx 입구 하나뿐입니다(D-29). M2 시연은 로컬이 기본이고, 공개 주소는 현장 네트워크에서 될 때만 보여 줍니다 |
